# Мониторинг

## `/api/health`

`GET /api/health` — без авторизации. Проверяет, что процесс достаёт до БД
(`SELECT 1`, таймаут 5 с, без ретраев — чтобы падать быстро и честно).

- `200` → `{ "status": "ok", "db": "ok", "env": "production", "latencyMs": 12, "time": "..." }`
- `503` → `{ "status": "error", "db": "down", ... }`

`env` — из `APP_ENV`, помогает не перепутать контур.

## Что чем ловится

| Сбой | Ловит |
|---|---|
| Весь деплой лежит (Vercel, сборка, сеть) | внешний монитор по `/api/health` |
| Приложение живо, но БД зависла (типичная болячка Neon) | тот же `/api/health` → `503` |
| Кривой деплой (ошибка при старте модуля, напр. `MINIAPP_DEV_BYPASS` в проде) | приложение не поднимется → внешний монитор |

## Внешний монитор

Любой из бесплатных: **UptimeRobot** или **Better Stack (Uptime)**.

1. Monitor type: HTTP(s), URL — `https://<домен>/api/health`, интервал 1–5 мин.
2. Считать «down» по коду ответа ≠ 2xx (оба сервиса умеют) — тогда `503` от
   health засчитается как падение.
3. Порог алерта — 2–3 подряд неудачных проверки (чтобы одиночный блип Neon
   не будил ночью).
4. Канал алерта — Telegram: у обоих сервисов есть встроенная интеграция;
   направить в чат/на аккаунт админов (тот же `ADMIN_TELEGRAM_ID`, если это
   личка, или отдельный чат).
5. Завести отдельные мониторы на прод и на staging.

## Возможное дополнение (не сделано)

Vercel Cron `/api/cron/healthcheck`, который сам делает проверку БД и при
сбое пишет админу в Telegram напрямую — ловит «БД легла, приложение живо»
без внешнего сервиса. Требует хранить последнее состояние (строка в БД или
KV), чтобы не спамить алертом каждую минуту. Пока полагаемся на внешний
монитор.
